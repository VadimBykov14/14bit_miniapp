# Витрина поставщика в MAX

[![Tests](https://github.com/VadimBykov14/14bit_miniapp/actions/workflows/tests.yaml/badge.svg)](https://github.com/VadimBykov14/14bit_miniapp/actions/workflows/tests.yaml)
[![Deploy](https://github.com/VadimBykov14/14bit_miniapp/actions/workflows/runner.yaml/badge.svg)](https://github.com/VadimBykov14/14bit_miniapp/actions/workflows/runner.yaml)

Мини-приложение и бот MAX, через которые магазины заказывают у поставщика. Заявка магазина сразу становится «Заказом клиента» в 1С. Проект сделан для хакатона Минобрнауки × MAX, трек «Эффективный бизнес».

- Стенд: https://14-bit-max.ru
- Бот: [@t7_hakaton_max_bot](https://max.ru/t7_hakaton_max_bot)
- Продукт и принятые решения: [docs/product/concept.md](docs/product/concept.md)
- Правила продукта: [business_logic.md](business_logic.md)
- Подключение настоящей 1С: [docs/1c-connection.md](docs/1c-connection.md)
- Устройство кода и правила разработки: [docs/development.md](docs/development.md)

> **Тестовые данные.** Демо-поставщики, витрины, магазин, заказы, база 1С и тестовые боты на стенде — тестовые и помечены в интерфейсе плашкой «Тестовые данные». Настоящая 1С на стенде не подключена: её заменяет строгий эмулятор `mock-1c` с тем же интерфейсом OData, что у «Управления торговлей 11».

## Назначение

Поставщик в небольшом городе — оптовая база, пекарня, кулинария — принимает заявки от постоянных клиентов: магазинов, киосков, кафе. Сейчас заявки приходят по телефону и в мессенджерах, менеджер перебивает их в 1С и обзванивает, чего нет.

Решение переносит этот цикл в MAX. Поставщик заводит витрины с ценами, остатками и графиком доставки, магазин собирает заявку в мини-приложении, а в 1С сразу появляется «Заказ клиента». Подтверждение, отгрузка и приёмка тоже идут в MAX и отражаются в 1С.

## Основной пользовательский сценарий

1. Поставщик открывает бота, заводит предприятие и витрину — вручную или из своей 1С.
2. Поставщик приглашает магазин ссылкой `max.ru/<бот>?start=<код>` в выбранную витрину. Магазин может и сам попроситься в витрину своего города.
3. Магазин собирает корзину и оформляет заявку на дату доставки. В 1С появляется «Заказ клиента».
4. Поставщик получает уведомление в MAX, подтверждает заявку (может поправить количества) или отказывает с причиной. Заказ в 1С переходит «К выполнению» и проводится.
5. Поставщик отмечает отгрузку, магазин — приёмку. Расхождения приёмки уходят комментарием к заказу в 1С.

## Состав и архитектура

### Роли

| Роль | Кто | Что делает |
|---|---|---|
| `owner` | владелец поставщика | витрины, цены, клиенты, сотрудники, подключение 1С |
| `manager` | сотрудник поставщика | принимает и ведёт заявки |
| `client` | владелец магазина | заказывает, принимает поставки, приглашает работников |
| `worker` | работник магазина | заказывает от имени магазина |

Аккаунт MAX — либо поставщик (владелец, менеджер), либо магазин (владелец точки, работник). Личность берётся только из подписи данных запуска MAX.

### Контейнеры

`docker compose`, семь контейнеров:

| Сервис | Образ | Что делает |
|---|---|---|
| `caddy` | `caddy:2-alpine` | HTTPS и маршрутизация: `/api/*` → api, `/webhook*` и `/health` → bot, `/1c*` → эмулятор 1С, остальное → miniapp |
| `api` | сборка `services/api` | FastAPI + SQLAlchemy async + Alembic. Вся бизнес-логика, обмен с 1С по OData (`app/onec`), уведомления, живые обновления по сокету, тестовые боты (`app/testbots.py`) |
| `bot` | сборка `services/bot-service` | вебхук MAX, уведомления с кнопками, приглашения, ограничение частоты запросов к API MAX |
| `mock-1c` | сборка `services/mock-1c` | строгий эмулятор OData «Управления торговлей 11» и кабинет тестовых баз `/1c` |
| `miniapp` | сборка `services/miniapp` | мини-приложение: React 19 + Vite + HeroUI + Tailwind, статика за Caddy |
| `db` | `postgres:16-alpine` | основная база |
| `s3` | `quay.io/minio/minio` | фото позиций и витрин, логотипы, снимки приёмки |

Как идут запросы: MAX открывает мини-приложение по адресу стенда → приложение ходит в `api` с подписью MAX → `api` пишет в Postgres и MinIO, выгружает заказы в 1С (на стенде — в `mock-1c`) и просит `bot` отправить уведомление → `bot` пишет людям через API MAX. Нажатия кнопок и запуск бота MAX присылает вебхуком в `bot`.

## Запуск

### Что нужно

- Docker Engine с Compose v2 (`docker compose`).
- Для работы в MAX — то, что в Docker не воспроизводится:
  - свой бот MAX и его токен из кабинета партнёра;
  - домен с DNS-записью на сервер и свободные порты 80 и 443. Caddy сам получает сертификат Let's Encrypt, а MAX принимает вебхуки только по HTTPS с настоящим сертификатом;
  - адрес мини-приложения `https://<домен>` в настройках бота на платформе MAX.

Без этих условий стек всё равно поднимется, но войти в приложение не получится: вход — только по подписи данных запуска MAX, а MAX открывает мини-приложение по адресу, который задан у бота. Поэтому основной сценарий проверяется на стенде в MAX, а локальный запуск показывает, что проект собирается и работает. Для такой проверки достаточно заглушек: любой токен и секрет и `BOT_DOMAIN=localhost` — Caddy выпустит для него свой сертификат.

### Одна команда

```bash
cp .env.example .env     # вписать значения — см. «Переменные окружения»
docker compose up -d --build
```

Для своего бота и домена один раз зарегистрируйте вебхук:

```bash
docker compose run --rm bot python set_webhook.py
```

> Не запускайте `set_webhook.py` с токеном бота стенда и другим доменом: вебхук бота переедет, и стенд перестанет получать запуски бота и нажатия кнопок. Сам `docker compose up` вебхук не трогает.

Что должно получиться:

- `docker compose ps` — все семь контейнеров запущены, у `api`, `bot` и `mock-1c` статус `healthy`;
- `curl https://<домен>/api/health` → `{"status":"ok"}`;
- `curl https://<домен>/health` → `"status": "ok"` и имя бота; с неверным токеном — `"degraded"`, контейнер при этом работает.

### Переменные окружения

Обязательные — без них `docker compose` не запустится и назовёт, чего не хватает:

| Переменная | Что это |
|---|---|
| `MAX_BOT_TOKEN` | токен бота MAX. Им же проверяется подпись данных запуска мини-приложения |
| `BOT_DOMAIN` | домен, на котором Caddy поднимает HTTPS и куда MAX шлёт вебхук |
| `WEBHOOK_SECRET` | секрет вебхука: запросы без него бот отклоняет |

Необязательные — у всех есть значения по умолчанию в `docker-compose.yml`:

| Переменная | По умолчанию | Что это |
|---|---|---|
| `POSTGRES_PASSWORD` | `max26` | пароль Postgres. Задаётся один раз: том базы создаётся с ним |
| `MAX_API_BASE` | `https://botapi.max.ru` | адрес API MAX |
| `ONEC_SECRET` | токен бота | ключ шифрования паролей своих баз 1С |
| `DEMO_MAX_USER_ID` | аккаунт демо-стенда | `user_id` MAX, которому сид выдаёт демо-роли. Для своей копии укажите свой |
| `ONEC_MODE` | `odata` | обмен с 1С: `odata` — по стандартному OData, `simulated` — без эмулятора |
| `ONEC_URL` | `http://mock-1c:8080/demo` | база 1С демо-предприятия |
| `ONEC_STAND_URL` | `http://mock-1c:8080` | эмулятор, в котором ищутся тестовые базы по ключу |
| `ONEC_USER` | `exchange` | пользователь обмена с тестовой базой |
| `ONEC_DEMO_KEY` | `demo.stand-demo-key` | ключ тестовой базы «Демо» в эмуляторе — тестовое значение |
| `ONEC_PRICE_KIND` | `Оптовая` | вид цены номенклатуры в 1С |
| `APP_TIMEZONE` | `Europe/Moscow` | часовой пояс отсечек и дат доставки |
| `AUDIENCE_INVITES_PER_DAY` | `20` | сколько приглашений в день поставщик рассылает ботом |
| `TEST_BOTS` | `1` | тестовые боты для проверки; `0` — выключить |
| `TEST_BOTS_BASES` | тестовая база стенда | слаги тестовых баз 1С через запятую: к новым витринам на них приходит бот-магазин. Пусто — любая тестовая база, кроме «Демо»; в `.env.example` пусто |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET` | `max26`, `max26secret`, `max26` | доступ к MinIO. На открытом сервере смените |

В `.env.example` рабочих токенов, паролей и ключей нет. Настоящий `.env` живёт только на сервере.

### Порты

Наружу открыт только Caddy:

| Порт | Что |
|---|---|
| 80 | выпуск сертификата и переадресация на HTTPS |
| 443 | всё приложение: `/` — мини-приложение, `/api/*` — API, `/webhook` — вебхук MAX, `/health` — состояние бота, `/1c` — кабинет тестовой 1С |

Внутри сети compose: `api`, `bot`, `miniapp` и `mock-1c` — 8080, `db` — 5432, `s3` — 9000.

### Зависимости

- Образы: `postgres:16-alpine`, `quay.io/minio/minio`, `caddy:2-alpine`; сборка — на `python:3.12-slim` и `node:22-slim`.
- Python: `services/api/requirements.txt` и `services/bot-service/requirements.txt`, версии закреплены точно. У эмулятора 1С версии записаны в его `Dockerfile`.
- Мини-приложение: `services/miniapp/package.json` и `package-lock.json`, сборка через `npm ci`.

### Остановка и повторный запуск

```bash
docker compose stop              # остановить, контейнеры остаются
docker compose start             # запустить снова
docker compose down              # удалить контейнеры; данные в томах сохраняются
docker compose up -d             # поднять заново с теми же данными
git pull && docker compose up -d --build   # обновить код; миграции применятся при старте api
docker compose down -v           # удалить всё, включая базу, фото, базы 1С и сертификаты
docker compose logs -f api bot   # логи
```

После `down -v` следующий запуск создаст базу и демо-данные заново.

## Внешние сервисы и интеграции

| Сервис | Зачем | Если недоступен |
|---|---|---|
| Платформа MAX | открывает мини-приложение и подписывает данные запуска — это вход в приложение | работа в MAX невозможна; в Docker не воспроизводится |
| API ботов MAX, `botapi.max.ru` | сообщения бота, кнопки, вебхук | уведомления не уходят в MAX, но остаются в ленте приложения |
| Библиотека MAX для мини-приложений, `st.max.ru/js/max-web-app.js` | мост к клиенту MAX: данные запуска, «Поделиться», вибрация | мини-приложение не получает подпись и не пускает |
| Let's Encrypt | сертификат для домена, выпускает Caddy | Caddy не поднимет HTTPS, MAX не примет вебхук |
| Справочник городов hh.ru, `api.hh.ru/suggests/areas` | подсказки при выборе города | остаётся встроенный список крупных городов, ответы кэшируются на сутки |
| 1С: УТ 11, КА 2, ERP 2 по OData | номенклатура, цены, остатки, «Заказ клиента» | заказ остаётся в приложении и уходит в 1С повторно, очередь — в «Обмене с 1С» |

На стенде и в Docker вместо настоящей 1С работает эмулятор `mock-1c`. Он отклоняет то же, что отклонит настоящая УТ: запросы без обязательных параметров и GUID, проведение без обязательных реквизитов, чужое имя пользователя.

## Работа с данными

- **Postgres** — предприятия, витрины, позиции и цены, подключения, приглашения, заявки, шаблоны заявок, уведомления, избранное. Схема — миграции Alembic в `services/api/migrations`, применяются сами при старте `api`.
- **MinIO** — фото позиций и витрин, логотипы, снимки приёмки. Файл — до 8 МБ.
- **Эмулятор 1С** — базы, номенклатура, остатки и пришедшие документы, файл `/data/bases.json` в томе `onec_data`.
- **Доступ.** Личность — только из подписи данных запуска MAX в заголовке `X-Max-Init-Data`, подпись действует сутки. Роль выбирается заголовком `X-Active-Role` среди тех, что у человека есть. Магазин видит только витрины, к которым подключён, поставщик — только своих клиентов и свои заявки.
- **Какие личные данные хранятся:** `user_id` и имя из MAX, телефон, город и адрес, которые человек вписал сам. Пароли своих баз 1С хранятся зашифрованными и обратно не отдаются.

## Тестовые данные

- **Демо-данные** создаёт при первом запуске `services/api/app/seed.py`: поставщики «Кондитерская база «Сладкий дом»» (витрина «Кондитерский опт» — из 1С, со склада) и «Пекарня «Хлебный двор»» (витрина «Пекарня» — вручную, под заказ), магазин «Магазин «У дома»», позиции, история заказов и акция «Опт от 3 000 ₽». Роли в демо получает аккаунт `DEMO_MAX_USER_ID`. Всё помечено «Тестовые данные».
- **Тестовая 1С.** Эмулятор сам создаёт базу «Тестовая база «Демо»» с ключом `ONEC_DEMO_KEY`. Новые тестовые базы заводятся в кабинете `https://<домен>/1c`: у каждой свой ключ вида `база.секрет`. Ключ вписывают при создании витрины в поле «Ключ базы 1С» — витрина загружает из этой базы позиции, цены и остатки, а заказы магазинов появляются в кабинете как «Заказ клиента». У каждой базы свои контрагенты — три тестовых, новые добавляются в кабинете; из них поставщик выбирает контрагента, когда подключает магазин к витрине на 1С.
- **Тестовые боты** (`services/api/app/testbots.py`) играют вторую сторону сценария, чтобы его можно было пройти одному:
  - «Тестовый поставщик (бот)» с витриной «Тестовая» — её видят магазины любого города. Через 15 секунд бот подключает магазин, который попросился, и подтверждает его заявки;
  - «Тестовый магазин (бот)» — через 15 секунд просится в новую витрину на тестовой базе 1С. После подключения оформляет одну заявку по минимуму, а подтверждённую через 30 секунд принимает досрочно.

  Боты ходят в тот же API с подписью, которую выдаёт сервер, — проверки, уведомления и обмен с 1С у них те же, что у людей. Самих ботов в MAX нет: «Написать» у бота присылает карточку аккаунта демо-стенда — человека из команды. Остатки боты не пополняют.
- **На стенде** данные для первого входа и ключ тестовой базы — на служебном слайде презентации.

## Пошаговая проверка

Проверяется на стенде, в MAX — мобильном или веб-версии. Хватает одного аккаунта MAX: вторую сторону играют тестовые боты. Аккаунт — либо поставщик, либо магазин: чтобы пройти обе роли, нужны два аккаунта.

**Поставщик — магазин играет бот**

1. Откройте [@t7_hakaton_max_bot](https://max.ru/t7_hakaton_max_bot) и приложение. Данные для первого входа — на служебном слайде презентации. Выберите «Поставщик», впишите название предприятия, город и телефон.
   Ожидаемо: открывается главная поставщика с разделами кабинета.
2. «Витрины» → «Создать витрину»: название, режим «Со склада», дни доставки и ключ тестовой базы со служебного слайда в поле «Ключ базы 1С» → «Создать и загрузить из 1С».
   Ожидаемо: в витрине позиции, цены и остатки из тестовой базы.
3. Через 15–20 секунд «Тестовый магазин (бот)» просит подключения — приходит сообщение в MAX. «Главная» → «Подключения» → «Подключить» → выберите, кто будет вести клиента → «Подключить».
   Ожидаемо: ещё через 15–20 секунд бот оформляет заявку — сообщение «Новая заявка…»; в кабинете `/1c` заказ «на согласовании · без резерва».
4. «Заявки» → заявка → «Подтвердить». Количество можно уменьшить до минимума позиции или добавить до 5 %.
   Ожидаемо: заказ в 1С «К выполнению» и проведён, в кабинете — «в работе · товар в резерве».
5. Подождите 30 секунд.
   Ожидаемо: бот принимает заказ досрочно — сообщение «Заявка №… завершена: клиент принял товар полностью досрочно…».

**Магазин — поставщика играет бот**

1. Первый вход — как у поставщика, но выберите «Магазин»: название, город и телефон.
   Ожидаемо: на «Главной» — витрины города и витрина «Тестовая» с пометкой «Тест»: она видна в любом городе.
2. «Тестовая» → «Запросить подключение».
   Ожидаемо: через 15–20 секунд бот подключает магазин — сообщение «Поставщик подключил вас к витрине «Тестовая»».
3. «Тестовая» → позиции в корзину (шаг — упаковка, не меньше минимума позиции) → «Перейти в заявку» → дата в календаре → «Отправить заявку».
   Ожидаемо: заявка в «Заказах», через 15–20 секунд бот её подтверждает.
4. «Заказы» → заявка → «Принять досрочно» → «Принять заказ» → «Да, принял всё».
   Ожидаемо: заявка завершена.

**Полный цикл на двух аккаунтах**

1. Поставщик: «Главная» → «Подключения» → «Пригласить клиента ссылкой» → выбрать витрину → «Отправить в MAX» или «Скопировать».
   Ожидаемо: ссылка вида `max.ru/t7_hakaton_max_bot?start=inv_…`.
2. Магазин открывает ссылку, бот присылает приглашение → «Принять приглашение».
   Ожидаемо: магазин подключён к витрине, поставщику приходит уведомление.
3. Магазин оформляет заявку, поставщик подтверждает — как выше.
4. Поставщик: «Отметить отгрузку». Магазин: «Принять заказ» — полностью или с расхождениями.
   Ожидаемо: заявка завершена, расхождения — комментарием к заказу в 1С.

### Примеры ожидаемого поведения при ошибках

- Количество меньше минимума или не кратное упаковке набрать нельзя; сервер такую заявку тоже отклонит с объяснением.
- Остаток уменьшился, пока заявка ждала, — подтверждение скажет, сколько осталось на складе, и попросит уменьшить количество.
- 1С не ответила — заявка сохранена в приложении, выгрузка повторится сама; очередь видна в «Обмене с 1С».
- Приложение открыто не из MAX — «Откройте витрину из MAX»; подпись старше суток — «Откройте приложение заново».
- Поставщик открыл ссылку для магазина или магазин — ссылку в команду поставщика: приглашение не срабатывает, бот объясняет почему.

## API

Собственный API для автоматической проверки не заявляется: это внутренний интерфейс мини-приложения, отдельно им не пользуются. Поэтому openapi-файл и `DATA-API.yaml` к проекту не прикладываются — по брифу они нужны только решениям с собственным API.

- Все маршруты — под `/api`. Каждый запрос подписан данными запуска MAX в заголовке `X-Max-Init-Data`, роль — в `X-Active-Role`.
- `GET /api/health` отвечает без подписи: `{"status":"ok"}`.
- Схему OpenAPI генерирует FastAPI: `http://api:8080/openapi.json` внутри сети compose, наружу она не открыта.

Основные разделы:

- `orders` — заявки;
- `storefronts` — витрины для магазина;
- `owner` — кабинет поставщика;
- `public` — витрины города и приглашения;
- `me`, `onboarding`, `notifications`, `live` — сокет обновлений;
- `photos`, `templates`, `workers`, `favorites`.

## Интеграция с 1С

Обмен идёт по стандартному интерфейсу OData настоящей УТ 11, КА 2 и ERP 2, без доработки конфигурации:

- номенклатура, цены и свободные остатки — по расписанию и по сигналу;
- «Заказ клиента» создаётся при оформлении, правится при подтверждении и снимается при отмене.

Поставщик подключает свою базу в настройках витрины: адрес публикации, пользователь, пароль, версия конфигурации и реквизиты заказа, выбранные из списков самой базы. Резерв в 1С ставится сразу или при подтверждении — по выбору поставщика.

Подробно — [docs/1c-connection.md](docs/1c-connection.md).

## Известные ограничения

- Мини-приложение работает только внутри MAX: вход — по подписи данных запуска, в обычном браузере приложение не пускает. Своя копия требует своего бота, домена и вебхука.
- Один аккаунт MAX — либо поставщик, либо магазин. Вторую сторону играют тестовые боты; для цикла между людьми нужны два аккаунта.
- MAX не пишет тем, кто ни разу не запускал бота: такие уведомления остаются только в ленте приложения.
- Обмен с настоящей 1С проверен на строгом эмуляторе, на живой УТ ещё не запускался. Для УТ 11.5.7 и новее имя ресурса свободного остатка стоит сверить по `$metadata` своей базы.
- Демо-данные достаются одному аккаунту — `DEMO_MAX_USER_ID`.
